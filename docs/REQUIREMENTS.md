# AI Home Butler 需求文档（REQUIREMENTS）

更新日期：2026-10-27 ｜ 状态：阶段 0 完成

## 1. 项目愿景

在成熟开源智能家居基础设施（Home Assistant / ESPHome）之上，构建一个具备环境理解、长期记忆、
任务规划、安全执行和主动服务能力的 AI 家庭管家。**不重复造 Home Assistant，不重写语音引擎，
不做只会聊天的 Demo。**

## 3. 总体功能需求（长期）

1. 自然语言/语音理解用户意图，基于**真实家庭状态**决策。
2. 统一设备接入层（HA、ESPHome、ESP32 自制设备），LLM 不得直接连设备端口。
3. 长期记忆与用户偏好，可查看/修改/删除/导出，区分"用户陈述"与"模型推测"。
4. 多步骤任务规划，步骤可追踪、可中断、可验证。
5. 独立于提示词的程序化安全层：白名单、参数校验、确认、超时、防重放、执行后验证。
6. 主动服务（提醒、已授权自动化），区分"通知 / 已授权自动化 / 需确认 / 禁止自动"。
7. 语音交互复用成熟方案（HA Voice / Wyoming 生态）。
8. 结构化日志、Token 成本记录、健康检查、备份恢复。

## 4. 阶段 1 需求（当前范围）

在 Windows 上运行一个命令行 AI 管家，对接**模拟设备**，验证"LLM + 工具调用 + 安全执行"闭环。

### 4.1 功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| F1 | 命令行多轮对话 | 保留上下文，支持 /devices /help /exit |
| F2 | 可配置大模型 | .env 配置 base_url/key/model，兼容 OpenAI 接口规范的厂商均可替换 |
| F3 | 传感器查询 | 模拟温湿度传感器，数据带采样时间与新鲜度 |
| F4 | 设备状态查询 | 灯（开关/亮度）、风扇（开关/档位） |
| F5 | 设备控制 | 需用户确认后执行；拒绝则状态不变 |
| F6 | 执行后验证 | 控制后回读状态，状态未知/失败不得报成功 |
| F7 | 状态持久化 | 模拟设备状态存 JSON，重启不丢 |
| F8 | 错误处理 | API 错误/工具异常/无效参数均不崩溃、不死循环，如实告知用户 |
| F9 | 日志 | 滚动文件日志，含工具调用与 Token 用量，不记录密钥 |
| F10 | 自动化测试 | pytest + FakeLLM，覆盖工具校验/确认/拒绝/循环上限/LLM 故障 |

### 4.2 明确不做（本阶段）

完整语音、自定义 Web 前端、长期记忆数据库、多 Agent 框架、自动化引擎、真实高风险设备控制、
自训练模型、复杂部署体系（Docker 等）。

### 4.3 非功能需求

- **安全**：确认机制默认开启；高风险设备类别默认禁止；密钥只存 .env（gitignore）。
- **可测试**：LLM 与设备均为可注入接口，测试不触网、不触真机。
- **可维护**：模块分层清晰，单一职责，外部接口有类型定义。
- **可演进**：设备层与 LLM 层均为适配器接口，阶段 2/3 换实现不换调用方。

## 5. 阶段 1 验收场景（全部通过才算完成）

1. 问温度 → AI 调工具获取，不编造。
2. 问灯光状态 → AI 调工具读取。
3. 要求开灯 → 系统请求确认；拒绝后状态不变。
4. 确认后 → 状态改变且回读验证。
5. 执行失败/状态未知 → AI 不得报告成功。
6. 连续对话保留上下文。
7. API 中断 → 不崩溃、不无限循环，给出友好提示。
8. 模型反复调用工具 → 触达上限后被强制收敛，不死循环。
