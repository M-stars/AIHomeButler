## 0. 产品定义（用户需求原话 → 工程转译）

**一句话**：管家实体（树莓派）是唯一的"大脑"，PC/手机应用是它的**遥控器+配置台**——
配对一次，终身可用；设备直控不经过 AI，任务下达经过 AI；所有配置在应用里完成，
不需要用户碰配置文件。

| # | 需求 | 工程含义 |
|---|---|---|
| 1 | 同局域网配对，配对成功后跨网络免再配对 | mDNS 发现 + 配对码换令牌 + 云中转双通道（§2/§3） |
| 2 | 应用内**直接操控**智能家电，无需经过 AI | 新增设备直控 API，确认制豁免但全量审计（§4） |
| 3 | 通过**对话**向 AI 管家下达任务 | 已有 /api/chat、/api/task，零改动复用 |
| 4 | 配置 AI 模型：选厂商 → 输 Key → 自动获取模型列表 | 管家代理探测厂商 /models，多模型档案（§5.3） |
| 5 | 配置家庭成员与对应声音 | 已有声纹/音色 API，应用做 UI（§5.4） |
| 6 | 配置管家声音 | 已有音色库 API（克隆/预设/默认），应用做 UI（§5.4） |
| 7 | 配置管家 AI 个性化（人设） | 新增 persona 持久化 API（§5.5） |
| 8 | PC 端正常安装流程：下载器 → 选路径 → 下载安装 | PyInstaller onedir 主体 + 下载器向导（§6） |
| 9 | 手机端正常下载流程 | 安卓签名 APK 官网分发；iOS 见现实约束（§7） |

**非目标**（延续项目哲学）：应用不本地跑任何模型；不上应用商店（除非未来 iOS 强制）；
不重写管家服务端业务逻辑——应用只是 API 客户端。

## 1. 总体架构

```
┌─ PC 应用（Win）──────┐   ┌─ 手机应用（Android/iOS）──┐
│ pywebview 壳 + 托盘   │   │ Capacitor 壳 APK / PWA     │
│ 设备面板│对话│设置向导 │   │ 同一套页面，触控适配        │
└──────────┬───────────┘   └────────────┬───────────────┘
           │  ①LAN直连: http://<pi>:8080 + 设备令牌      │
           │  ②云中转:   https://butler.<你的域名> + 同一令牌
           ▼                             ▼
┌──────────────── 管家实体（树莓派，唯一权威）────────────────┐
│ FastAPI：对话/任务/确认队列/记忆/审计（已有）                 │
│ 新增：mDNS 广播 + 配对服务 + 设备直控 API + 设置 API 组        │
│ 持久化：pairings 表（设备令牌）、settings 表（模型/人设）       │
└──────────────────────────┬─────────────────────────────────┘
                           │ 出站隧道（管家主动外连，无入站端口）
                  ┌────────▼─────────┐
                  │ 阿里云 2C2G 枢纽  │ frp+HTTPS / WireGuard + ntfy 推送
                  └──────────────────┘
```

**双通道自动切换**（需求 1 的"跨网免配对"实现）：
应用连接管家时按序尝试 ① mDNS/上次 LAN 地址直连（超时 1.5s）→ ② 云端地址；
两条通道用**同一设备令牌**，切换对用户透明。管家在线即可用，与手机连哪个 WiFi 无关。

## 2. 发现与配对协议（首配必须在局域网）

### 2.1 发现：mDNS/DNS-SD

管家进程启动时用 python-zeroconf 广播：

```
服务类型: _aihomebutler._tcp.local.
TXT 记录: name=管家别名  ver=协议版本  phase=pairing|paired  fp=<指纹前8位>
端口: 8080
```

- `phase=pairing` 才允许新配对（可在设置里关闭发现广播，防陌生人配对）；
- 应用端：Android 用系统 NSD API、iOS 用 Bonjour、PC 用 zeroconf——零额外服务端。

### 2.2 配对流程（类 HomeKit，简化到家用强度）

```
应用                          管家
 │ 1. mDNS 发现 ←──────────────│ 广播 phase=pairing
 │ 2. 用户在应用输 6 位配对码    │ 配对码来源：管家界面设置页 /
 │    （POST /api/pair/start）  │ CLI `python -m butler pair` / 语音播报
 │ 3. POST /api/pair/confirm   │ 校验：码有效(10分钟/3次尝试/一次性)
 │    {code, device_name}      │ → 生成 device_id + device_token
 │ ←──────── {device_id, token}│ pairings 表落库（名称/时间/令牌哈希）
 │ 4. 凭证入系统安全存储         │ 审计: pairing.create
 │    Win凭据管理器/Keystore/Keychain
```

- 配对码**限时限次一次性**；管理端随时作废；
- 令牌按设备隔离：设置页可查看已配对设备列表、**踢除设备**（令牌即失效）；
- Web 已有单令牌鉴权机制升级为**多令牌**：`X-Butler-Token` 校验改为查
  pairings 表（主令牌 + 各设备令牌并存，主令牌保留给 CLI/调试）。

### 2.3 免再配对的持久性

- 配对记录在**管家侧** SQLite（pairings 表），重启/升级不丢；
- 应用侧凭证在系统安全存储，重装应用才需重新配对；
- 管家换 IP/换端口：mDNS 重新发现 + 云端域名固定，令牌不变，无感恢复。

## 3. 云中转（跨网访问，阶段 18 实施，阿里云 2C2G）

- **管家出站建隧道**：frpc（推荐，配置简单、断线自动重连）把 `localhost:8080`
  映射到云上 `https://butler.<域名>`（Nginx TLS 终结）；备选 WireGuard（更安全，
  应用需装 WG 配置，体验差一档）；
- **推送**：管家主动提醒/待确认 → HTTP 转发自建 ntfy（云上）→ 手机 ntfy App /
  应用内嵌订阅；**推送只带标题与计数，不带记忆内容与确认参数**（V1 安全设计延续）；
- 红线不变：管家 8080 绝不直接映射公网；云中转必须有 TLS + 令牌双重防线。

## 4. 设备直控（不经 AI）——确认制的豁免边界

### 4.1 新增 API

```
POST /api/devices/{device_id}/command   {action, value?}
→ 复用 ToolExecutor 执行路径（超时预算/防重放/回读验证全部生效）
→ 跳过 confirmer：界面按钮 = 用户本人意图，弹确认是荒谬的
→ 审计照记：actor=device_app:<device_id>（区别于 AI 路径 actor=ai）
GET /api/devices/{device_id}/state      单设备状态（面板刷新用，替代全量 overview）
```

### 4.2 安全边界（与既有架构对齐）

- 高风险设备类型（lock/water_heater/alarm/siren/garage door）**结构性不在白名单**，
  直控 API 对其返回 403——豁免只覆盖既有可控 8 类；
- 直控走同一执行器：防重放、超时、结果验证（verified/unknown）一个不少；
- 应用设备面板对"结果不明"状态如实展示（异步窗帘语义沿用阶段评审结论）。

## 5. 应用功能模块设计

### 5.1 首页/对话

对话流（/api/chat 轮询已有）+ 主动通知列表 + 待确认卡片（推送只报数，进应用看参数）。

### 5.2 设备面板（需求 2）

- 数据源即动态能力：`/api/overview` 每台设备带 `actions` 清单（阶段 14.5 自动发现从
  HA 能力位标志推导，新设备进网即出现），应用**按 actions 渲染控件**而非按类型写死——
  开关=切换、灯有 set_brightness=亮度滑条、窗帘有 set_position=位置滑条+开/停/关、
  空调=温度步进器、扫地机=按钮组；
- 状态轮询 2s（沿用），面板可见时只刷可见设备（/api/devices/{id}/state）。

### 5.3 AI 模型配置（需求 4）——厂商档案 + 自动探测

内置厂商档案表（全部 OpenAI 兼容协议，llm_client 零改动）：

| 厂商 | 默认 base_url | /models 探测 |
|---|---|---|
| DeepSeek（默认） | https://api.deepseek.com | ✅ |
| 月之暗面 Kimi | https://api.moonshot.cn/v1 | ✅ |
| 智谱 GLM | https://open.bigmodel.cn/api/paas/v4 | ✅（兼容端点） |
| 阿里通义 | https://dashscope.aliyuncs.com/compatible-mode/v1 | ✅ |
| OpenAI | https://api.openai.com/v1 | ✅ |
| 自定义 | 用户填 | 探测失败→手填模型名降级 |

流程：应用选厂商 → 输 Key → `POST /api/settings/models/probe`（**管家持 Key 代理探测**
/models，Key 不回传应用）→ 返回模型列表 → 用户选定主模型/规划模型 → `POST /api/settings/models`
保存 → 应用提示"已生效"（管家侧热重建 LLM 客户端，无需重启，见 §8）。

### 5.4 家庭成员与声音（需求 5/6）——全为已有 API 的 UI 化

- 成员列表 + 注册向导（录 3 段话 → /api/speakers）+ 每成员绑定音色（已有 voice_id 字段）；
- 管家声音：音色库列表/克隆（上传参考音频+文本+授权勾选）/预设音色/设默认；
- 声纹与音色的隐私红线原文不变（向量不出服务端、删除即清缓存）。

### 5.5 AI 个性化（需求 7）——新增 persona

- `GET/PUT /api/settings/persona`：管家系统提示词（当前硬编码"你是测试管家"升级为可配置）；
- 持久化 settings 表 + **热生效**（Conversation 构建时读取）；预置几个人设模板（默认管家/
  简洁模式/长辈模式）+ 自由编辑；编辑需确认（MEDIUM，防提示词注入面扩大）。

### 5.6 设置页其他项

管家别名、发现广播开关、已配对设备管理、通知免打扰时段、token 用量展示（已有）。

## 6. PC 端技术方案（需求 8）

### 6.1 应用主体

- **pywebview 壳**（V1 选型结论继续有效：Edge WebView2 渲染，前端零重写，~80MB 内存增量）；
  托盘常驻/关窗最小化/桌面通知/Ctrl+Alt+B 热键/开机自启——V1 已实现，从 desktop-shell
  分支合入并增强：新增配对向导页（首次启动：发现→配对码→完成）、连接状态指示（LAN/云）；
- **PyInstaller onedir** 打包（非 onefile：启动快 2-3s vs 8s+，排除 faster-whisper/sherpa/
  CosyVoice 等重依赖，目标体积 120-160MB）；frozen 路径适配（PROJECT_ROOT→exe 目录，
  数据/日志随安装目录，卸载器清理选项）。

### 6.2 安装分发：下载器向导（用户点名要的形态）

```
官网/Release 下载 setup.exe（~5MB 下载器，Inno Setup 制作）
  → 向导：许可 → 安装路径（默认 %LOCALAPPDATA%\AIHomeButler）→ 组件勾选
  → 下载器从 GitHub Release/阿里云 OSS 拉取 app-<ver>.zip（断点续传+SHA256 校验）
  → 就地展开 + 开始菜单/桌面快捷方式 + 卸载登记（Windows"应用和功能"可见）
  → 完成页：启动应用 → 进配对向导
```

- 版本升级：应用内检查更新 → 重新拉 zip 覆盖（下载器仅首装用）；
- 未联网安装兜底：Release 同时提供完整离线 setup.exe（内嵌主体，二选一下载）。

## 7. 移动端技术方案（需求 9）

### 7.1 Android（完整功能，正常分发）

- **Capacitor 壳**（同一套网页 + 原生插件：NSD 发现、通知、后台刷新），Gradle 打签名 APK；
- 分发：Pi 界面/官网提供 `app-release.apk` 下载 → 浏览器下载 → 允许未知来源安装
  （国内无 GMS 依赖，ntfy 推送用独立 App 或应用内嵌 ntfy 订阅）；
- 版本升级：应用内提示 + 重新下载 APK 覆盖安装。

### 7.2 iOS（硬现实：不上架无法正常分发）

如实给三条路，推荐 a 起步：

| 路线 | 成本 | 体验 |
|---|---|---|
| a. **PWA 添加到主屏**（同一套页面，Safari 打开→添加） | 0 | 90% 功能；推送用 ntfy 官方 App 兜底（iOS Web Push 受限） |
| b. Apple 开发者账号 + TestFlight | 99 美元/年 | 完整原生分发，需 Capacitor 出 iOS 包 |
| c. 企业签/自签 | 不稳定/7天过期 | 不推荐 |

### 7.3 推送

主动提醒/待确认 → 云 ntfy → 手机通知（标题+计数）；点开进应用看完整内容后操作，
**确认动作绝不做成推送快捷按钮**（V1 安全设计原文延续）。

## 9. 安全设计要点

- **配对**：6 位码 10 分钟/3 次/一次性；发现广播可关；踢除设备即时生效；
- **凭证**：应用端入系统安全存储，绝不落明文配置文件；管家端只存令牌哈希；
- **传输**：LAN 内 HTTP+令牌（家庭网可接受）；跨网必须 TLS（frp+Nginx 或 WireGuard 内）；
  红线：8080/CosyVoice 9880 绝不直接映射公网；
- **Key 保管**：LLM Key 只存管家侧（.env→settings 表迁移后加密落盘），应用只写不读，
  界面回显永远打码；
- **审计同源**：直控/配对/设置变更全落 audit_log，actor 区分 ai / device_app:<id> / user。

| 阶段 | 内容 | 依赖 |
|---|---|---|
| **15** | 管家侧：mDNS+配对服务+多令牌+直控 API+设置 API 组+LLM 热重建 | 无（Pi 上即可开发） |
| **16** | PC 应用：pywebview 壳增强（配对向导/连接状态/设备面板页）+ PyInstaller + 下载器安装包 | 阶段 15 |
| **17** | 移动端：Capacitor 安卓 APK（签名分发）+ iOS PWA 过渡 + 页面触控适配 | 阶段 15 |

（涉及公网，可独立回退）。Pi 部署（当前主线）与阶段 15 无冲突，可先行。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| 路由器 AP 隔离挡 mDNS | 应用支持手输管家 IP 配对兜底；引导用户关 AP 隔离 |
| 安装包体积大（~150MB） | onedir+按需组件；下载器带进度与断点续传；文档如实标注 |
| iOS 无法正常分发 | §7.2 三条路如实告知，PWA 先行 |
| 配对被局域网内陌生人利用 | 配对码限时限次 + 广播开关 + 设备管理踢除 + 管家仅家内网 |
| Key 泄露 | 只存管家侧、界面打码、审计记录、推送 GitHub 前扫描惯例不变 |
| frp 域名被扫描滥用 | TLS+令牌双防线；备选 WireGuard；云安全组限源 |
| LLM 热重建引入状态错乱 | 会话历史随 Agent 重建清空属可接受行为，UI 明确提示 |
